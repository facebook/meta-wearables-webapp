## What this is

A **webapp game** for Meta Display Glasses (also runs in a desktop browser for
development). The glasses have a 600x600 additive waveguide display — pure black is
transparent, only bright pixels show — and EMG Neural Band + Captouch D-pad input.

## Platform & framework knowledge

When planning or implementing work in this repo, use the **`read-webapp-game-docs`**
skill (from the `meta-wearables-webapp-game` plugin) to find relevant knowledge before writing
code — both about the **Meta Display Glasses platform** (600x600 additive display, performance budgets,
EMG/D-pad input) and about the **`meta-wearables-webapp-game` framework** (renderer/input-agnostic
architecture, project structure, Three.js-vs-DOM split, localization, asset loading). Prefer it
over guessing whenever a change touches platform constraints or the framework's conventions.

For **improving** the game rather than extending it — polish, feel, pacing, "what should I do
next", "is this ready?" — use the **`webapp-game-director`** skill from the same plugin. It
surveys the build against a quality rubric, ranks the issues, and works them one at a time with a
real playtest deciding each one. It maintains `docs/critique.md` (the milestone board) and
`docs/playtest-log.md`.

## Tech stack

- **Vite** + **TypeScript** (strict). Path alias `@/* -> src/*`.
- **Three.js** for the game world (2D or 3D), used **only** behind the `Renderer` interface.
  2D uses an orthographic camera + sprites; 3D uses a perspective camera + meshes.
- **Vitest** for unit tests.

## Commands

- `npm run dev` — Vite dev server with HMR (desktop at `localhost:5173`).
- `npm run typecheck` — `tsc --noEmit` (the real type gate; Vite strips types without checking).
- `npm test` — the whole Vitest suite: this game's tests plus the framework tests the scaffold
  shipped. Its total is not a measure of how well this game is tested.
- `npm run test:game` — only this game's own tests (everything outside `src/framework/`).
- `npm run test:framework` — only the scaffold's framework tests.
- `npm run build` — `tsc --noEmit && vite build` -> `dist/`.
- `npm run validate` — project guideline checks: no input handled via the DOM, all user-facing
  text localized, no runtime network asset loads, and no raw `console.*` in game code.

Run `typecheck`, `test`, `build`, and `validate` before considering a change done.

## Deploying

Vercel: deploy from the **project root** — Vercel auto-detects Vite and runs `npm run build`.
The root `vercel.json` gives SPA fallback and the cache policy. Never add a `server.js` /
`package.json` `start` script (Vercel would run the app as a Node function and 404 every route),
and never move `vercel.json` into `dist/` (Vite empties it on each build).

Caching is keyed on Vite's content hashes, which is why `vite.config.ts` sets
`build.assetsDir: '_vite'`: the bundler's hashed output is the only thing under `/_vite/`, so that
tier is `immutable` (a new build is a new URL). `/api/*` is `no-store`, and everything else —
`index.html` and the verbatim-copied `public/` assets — is `no-cache`, i.e. stored but revalidated
on every load, so a republish is picked up immediately. **Don't point the immutable tier at
`/assets/`**: `public/` is copied into the build root, so `public/assets/...` would land under the
same prefix and a verbatim file with a stable URL would be frozen for a year with no way to bust
it. Don't widen the last tier to a long `max-age` either, for the same reason. See the README's
*Caching* section.

`npm run build` also emits `dist/sw.js` (via `scripts/vite-service-worker.mjs`), a service worker
that precaches the build so a second launch reads from disk and the game runs offline. The precache
list is generated by scanning `dist/`, so it needs no maintenance as `public/` grows, and each file
is keyed by a content hash — a republish re-downloads only what changed, despite `public/`
filenames being stable. It is off in `npm run dev`; `?swreset=1` wipes the worker and its caches.
See the project docs' `offline-caching.md`.

## Architecture (do not break these boundaries)

Gameplay logic is **renderer-agnostic and input-agnostic**. Reusable engine code lives under
`src/framework/` (managed — re-copyable, don't hand-edit; it imports no game code). Everything
else in `src/` is game code you own.

- `src/framework/render/Renderer.ts` — rendering contract, generic over the game's model-id
  union. `src/framework/render/ThreeRenderer.ts` builds geometry from a catalog (with a
  selectable 2D orthographic / 3D perspective camera) and, together with
  `src/framework/render/AssetLoader.ts` and `src/models.ts`, is one of the only three places
  that import `three`. Entities/systems never do. (`render/assetFormats.ts` is `three`-free.)
- `src/framework/render/AssetLoader.ts` — loads textures (PNG/WebP/JPG) and 3D models
  (GLB/GLTF/FBX/OBJ). See the project docs' `asset-loading.md` for the preload-then-clone pattern.
- `src/models.ts` — the game's model ids + Three.js geometry (the `MODELS` catalog). Add
  models here, not in the framework.
- `src/framework/input/InputManager.ts` — input contract. `PointerKeyboardInput.ts` is the
  only input file that touches DOM events.
- `src/framework/sw/` — the service worker. `precache.ts` is the engine (takes its `CacheStorage`
  and `fetch` as arguments, so it is node-testable), `service-worker.ts` is the worker entry the
  build bundles into `dist/sw.js`, and `register.ts` is the page-side call `main.ts` makes. Never
  await that call: precaching benefits the *next* launch, so blocking startup on it is backwards.
- `src/core/` — gameplay + orchestration. `src/hud/` — DOM HUD/menus (no Three.js).
- `src/i18n/` — UI strings (`en.json`) + i18next bootstrap. All user-facing text is localized
  (see Localization below); the framework's i18next setup lives in `src/framework/i18n/`.
- `src/config/gameplayConstants.ts` — **all** tunable numbers as named constants. Never
  inline magic numbers. The framework classes receive the few numbers they need via
  constructor options (wired in `main.ts`); framework code never imports config.

This is what makes gameplay unit-testable (see `src/core/Game.test.ts`, which drives `Game`
with fake renderer + input — no GPU, no DOM). The fakes live in `src/framework/testing/fakes.ts`:
import them rather than writing your own.

Two things outside `src/framework/` are also managed and must not be hand-edited or deleted:
`src/framework/VERSION` and the `<meta name="generator">` tag in `src/index.html`. The tag is the
attribution marker that reaches the built game — it records the skill and version that produced
it, and links to <https://github.com/facebook/meta-wearables-webapp>. The framework-update skill
re-stamps both; `npm run validate` fails if the tag goes missing.

## Three.js vs DOM

Game world (2D or 3D) -> Three.js canvas. UI/HUD/menus/text -> DOM overlay. Never render text
in WebGL.

## Localization

All user-facing text goes through **i18next**. Add strings to `src/i18n/en.json`, then render
them with `t('key')` from `@/i18n` (dynamic text) or a `data-i18n="key"` attribute on an empty
element (static HTML). Never hardcode user-facing copy in the DOM — `npm run validate` fails on
it. Bare numbers (`String(score)`) and glyph-only labels are not copy and stay as-is. Implement
**English only**; the setup lets a translator add `<lang>.json` later with no code changes. The
locale is auto-detected (device language; `?lng=<code>` overrides it for testing). See the
project docs' `localization.md` (via `read-webapp-game-docs`).

## Input model

Input is two EMG gesture families (a desktop keyboard reproduces both):
- **Index pinch** (thumb→index pad): a quick pinch is a SELECT → `pinchTap`. The device emits
  `Enter` for it, but whether the framework listens to `Enter` or to a click depends on the mode
  derived below. A pinch-and-move is a drag → `pinchBegin`/`pinchEnd` + a movement delta, but
  ONLY if `<body>` sets `touch-action: none` and the input is `{ pointerDrag: true }` (opt-in;
  tap-only games skip it).
- **D-pad** (thumb→index side): a swipe → `dpadSwipe` (arrow keys). There is no discrete
  center ("thumb") tap — the device emits `key="Unidentified"` for both swipes and side taps,
  so it's ambiguous and ignored.

The discrete select is the index pinch (`pinchTap`) — never map `Enter` to the D-pad. How a
drag maps to gameplay is game-dependent.

**Iterating in a browser: run `node scripts/validate-drag-optin.mjs` from the project root to see
which mode this game is in** — it prints `mode: tap-only` or `mode: drag (opted in)` on stderr.
The exit code answers a different question: it reports whether the opt-in is *coherent*. Exit 1
means the three edits disagree, not that the mode is unknown. Exit 2 is a usage error — a path
that isn't a directory, an unknown option — and says nothing about the game at all; fix the
invocation and re-run rather than reading it as an incoherent opt-in. A wrong working directory
is not an error: it scans that directory, finds nothing, and reports `mode: tap-only`, so check
the `scanned N file(s) under <dir>` line before believing the mode.

Read the `note:` and `AMBIGUOUS` lines alongside the `mode:` line, because the mode is only
derived when the script can see the opt-in. It reports `mode: tap-only` and exits 0 in two cases
where it could not decide, and each needs a different follow-up:

- an `AMBIGUOUS` entry for a `pointerDrag` that is not a boolean literal — the entry names the
  `file:line` it found; read the value there and work out what it evaluates to;
- a `note:` saying the project builds its own `InputManager` (no `new PointerKeyboardInput(...)`
  to read) — there is no `pointerDrag` option to find, and it need not be in `src/main.ts` at
  all. Read wherever that manager is constructed and configured, and check the same three things
  by hand: `touch-action: none` on `<body>`, whether the manager listens for the pointer stream,
  and whether the game consumes a movement delta.

Either one means the mode is unknown, not tap-only. Do not assume a gesture until you have
settled it.

In tap-only, the pinch is `Enter` and a mouse click is not an input at all; that is correct —
there is no cursor on the glasses. In drag mode the pinch is a click and `Enter` is deliberately
ignored, so the device's two channels can't double-fire.

**Never turn on `pointerDrag` to make clicks select.** That flag opts into the device's
pinch-and-move pointer stream and moves the tap source off `Enter`; it belongs on only if a drag
drives gameplay, and `npm run validate` fails a game that sets it without consuming the movement
delta.

**No input through the DOM.** The DOM is display-only (the HUD reads state and writes DOM).
Never put input handlers on DOM elements — no inline `on*=` HTML attributes, no
`addEventListener` for input events, no `el.on<event> =` assignments. All input flows through
the `InputManager` and is consumed from the game loop; the only file that touches DOM input
events is `src/framework/input/PointerKeyboardInput.ts`. `npm run validate` enforces this.

## Logging

There is **no console on the glasses** and no way to attach one. So game code logs through the
shared logger, never `console.*` (`npm run validate` fails on a direct console call):

```ts
import { log } from '@/log';
log.info('level started', { level: 3 });
```

Levels are `error`/`warn`/`info`/`debug`/`trace`; the default is `warn`, and `?log=debug` raises it
for a session. `?logview` draws the last lines on the display itself — the fastest way to see
what's happening on device. Never log in `update()` without an `if (log.isEnabled('debug'))` guard:
it runs 60×/second. To read device logs on a laptop, add the backend with the
`add-webapp-game-logging` skill. See the project docs' `logging.md` (via
`read-webapp-game-docs`).

## Display & performance budgets

Keep within: 600x600 viewport, black page background (transparent on device), dark gray only on
bounded surfaces (cards, panels, modals) and no background fill behind the always-on HUD, HUD
text >= 16px, 30 fps, JS < 500 KB gzipped, runtime memory < 128 MB. Stop the loop/animations when
idle.
