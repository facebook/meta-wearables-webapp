# Offline and precaching (the service worker)

A scaffolded game ships a **service worker** that precaches the whole build. The first launch fills
the cache; every launch after reads the game off disk, and it works with the Wi-Fi off. It is on by
default and needs no configuration — the precache list is generated from the build output.

This is a different layer from [`loading-screen.md`](loading-screen.md)'s `preloadManifest`, and
they work together:

| | `preloadManifest` | the service worker |
|---|---|---|
| Holds | decoded assets in **memory** (textures, `AudioBuffer`s) | compressed **bytes on disk** (`CacheStorage`) |
| Lifetime | the game session | across launches, until the build changes |
| First launch | downloads everything | fills the cache |
| Second launch | downloads everything again → **reads from the cache** | serves it |
| Offline | fails → **works** | works |

`preloadManifest` is unchanged and still does its job; the worker just means it stops being
network-bound after the first run.

## Why this exists

Startup latency is the headline gap between a web app and a native one on the glasses — 650 ms
native vs 3900 ms web in the 2048 parity study, against an org target of TTFI < 3 s. A per-app
service worker closes most of it, and the behaviour it depends on is this:

**On an offline cold start the browser loads the page rather than showing its own no-connection
screen**, so the worker gets the chance to answer from `CacheStorage`. Without that, a worker is
never consulted and the game is simply unavailable offline. Everything below assumes it.

## Where the precache list comes from

**It is generated by scanning `dist/` after the build**, in
`scripts/vite-service-worker.mjs` — *not* by reading the game's `preloadManifest` asset manifest.

That is deliberate. The asset manifest is opt-in, lives at a path only convention fixes, and never
covers the app shell (`index.html` plus the hashed bundle), which is most of a cold start. Vite has
already copied everything from `public/` into `dist/` by the time the plugin runs, so scanning the
build is a strict superset of the manifest, works for a game that declares no manifest at all, and
yields a real content hash per file — which is what makes the update model below work.

Nothing to maintain: adding a texture to `public/` puts it in the next build's precache list.

## Updates: the revision is the version, not the URL

A game's asset filenames are stable — `sprites/hero.png` stays `sprites/hero.png` across builds — so
the URL cannot carry the version. Each file is cached under its URL **plus a `__precache_rev` query
parameter holding the sha256 of its bytes**, and the generated `sw.js` embeds that list:

```js
const PRECACHE = [
  { url: 'index.html',            rev: 'ab12…', shell: true },
  { url: '_vite/index-A1b2.js',   rev: 'cd34…', shell: true },
  { url: 'sprites/hero.png',      rev: 'ef56…' },
];
```

The chain that makes a republish land:

1. A file's content changes, so its `rev` changes, so **`sw.js`'s bytes change**.
2. The browser re-fetches `sw.js` on navigation and byte-compares it. Different → install the new
   worker. Identical → nothing happens, and no asset traffic at all.
3. Install copies every entry whose revision is unchanged **straight across from the old cache**,
   and fetches only the ones that moved.

So a republish costs only what actually changed. Measured on a scaffolded game with two builds
differing by one `public/` texture: build 1's install downloaded 5 files, build 2's downloaded 1.

Two things reinforce step 2 against a stale `sw.js` being served from the HTTP cache:
`updateViaCache: 'none'` on registration, and the `no-cache` header `vercel.json` already puts on
everything outside `_vite/`. Keep both — the header also covers clients that registered before the
option existed.

`registerGameServiceWorker` also calls `registration.update()` on launch and whenever the page
returns to the foreground, because a game is often resumed rather than navigated to.

## Serving strategy

Same-origin `GET`s only; everything else passes straight through.

- **Navigations → network-first**, falling back to the cached `index.html`. The entry HTML is about
  a kilobyte and served `no-cache`, so this is normally one conditional request answered `304` —
  cheap enough to buy the guarantee that a freshly published build is picked up on the launch it
  ships rather than the one after. Offline, the request fails immediately and the cached shell
  answers.
- **Everything else → cache-first.** A request carrying a query string the file was not cached with
  (`hero.png?v=3`) still resolves, because lookup canonicalizes the URL.

`skipWaiting` + `clients.claim` are safe here: a game loads its whole asset set in one pass at
startup, so there is no long-lived session that could straddle two revisions.

**A failed app-shell entry fails the install**, leaving the previous worker in place rather than
installing one that boots to a black screen offline. A failed game asset only warns, and the rest of
the build still caches.

## Bandwidth

Precaching a whole asset set is exactly the "every app pulls on every don" behavior the platform
worries about, so two things bound it: install downloads run through a **concurrency pool** (6 by
default) rather than opening one connection per file, and the carry-over above means the
steady-state cost of a republish is only the changed files, not the payload.

If a game has a large optional download it does not need cached, exclude it:

```ts
// vite.config.ts
serviceWorker({ exclude: ['assets/bonus-levels.pak'] });
```

## Development

**The worker is off in `npm run dev`.** A service worker alongside Vite's HMR produces stale-module
bugs that read as build failures. `registerGameServiceWorker` no-ops on a dev build, and the Vite
plugin is `apply: 'build'`. Use `npm run build && npm run preview` to exercise it locally —
`http://localhost` counts as a secure context, so no HTTPS setup is needed.

### `?swreset=1` — the escape hatch

Unregisters every worker for the origin, deletes **every** cache — not just this feature's — and
reloads with the flag stripped (so it cannot loop). The reloaded page then registers again and
precaches from scratch, so you land on a clean, freshly-filled cache rather than on no worker at
all. The one cost is that the next load is a cold one.

This matters more than it looks. The glasses have no reachable DevTools "Application → Clear
storage" button, so without an in-page way to do it a bad cache is unrecoverable short of clearing
the whole browser. Reach for it whenever a change on device stubbornly refuses to appear.

### The single-file artifact has no worker

`npm run package` emits a self-contained `index.single.html` that fetches nothing, so there is
nothing for a worker to precache. `package-single-file.mjs` therefore ignores `dist/sw.js` rather
than treating it as an un-inlined leftover — without that, the worker would fail `npm run ship` for
every procedural game. The multi-file `dist/` it is built from keeps its worker.

## Verifying it

On a desktop browser against `npm run preview`:

```js
navigator.serviceWorker.controller          // non-null once it has taken over
await caches.keys()                         // ['webapp-game-precache-<build>']
(await (await caches.open((await caches.keys())[0])).keys()).length   // file count
```

Then reload with the network throttled to *Offline* in DevTools — the game should still reach the
title screen. To prove the update path, change one file in `public/`, rebuild, reload, and watch the
Network panel: only that file should be requested.

On device, the same check is "launch, force-quit, turn Wi-Fi off, launch again". If something looks
stale, `?swreset=1` first.

## Where the code is

| File | Role |
|------|------|
| `src/framework/sw/precache.ts` | The engine: cache naming, cross-build carry-over, matching. Takes its `CacheStorage` and `fetch` as arguments, so it is unit-tested in plain Node. |
| `src/framework/sw/service-worker.ts` | The worker entry. Thin — it only binds the engine to the real worker globals. |
| `src/framework/sw/register.ts` | `registerGameServiceWorker`, `swResetRequested`, `resetServiceWorker`. Runs in the page. |
| `scripts/vite-service-worker.mjs` | Build step: scans `dist/`, hashes it, bundles the worker with the list injected. |

`src/framework/` is managed code — pull framework changes with
`update-webapp-game-framework` rather than hand-editing it.
